# ADR-0003 4軸のバージョン管理

## 状態

**Accepted**（2026-11-20、関連 Issue [#8](https://github.com/manabukosaka/sports-motion-app/issues/8)、[#24](https://github.com/manabukosaka/sports-motion-app/issues/24)）

## 背景

3D 動作解析では、同じ動画でもモデルやフィルタの更新で関節角度などの計測値が変わる。オフラインで撮影した端末は、撮影時と異なる API が稼働する環境で同期を再開することがある。LINE で共有したレポートは、文献 DB が更新されても指導時に参照した値を表示する必要がある。単一のアプリ版では、解析の再現条件、撮影データの互換性、共有時点の文献比較を追跡できない。[開発プロセス §4.5](../03-development-process.md#45-横断的エンジニアリング戦略検討強制フェーズ対応表)

## 決定

### 1. アプリ・共有 Web

モバイルアプリと共有 Web はそれぞれ SemVer（`MAJOR.MINOR.PATCH`）と単調増加する整数のビルド番号で配布物を識別する。モバイルではビルド番号を iOS の `CFBundleVersion` と Android の `versionCode` に設定する。

モバイルは API リクエストに `X-App-Version` を送り、API は `X-Minimum-Supported-App-Version` で対象プラットフォームの最低対応版を返す。最低対応版を下回る端末では同期を保留し、ストアでの更新後に送信を再開できることを案内する。オフライン撮影の動画と送信キューは撮影時の `contract_version` とともに端末に保持する。更新後のアプリは既存のキューを読み取り、必要に応じて API が受け付ける契約版に変換して再送する。キューからの削除はサーバーの受領確認後に行う。

### 2. API・共有データ契約

`packages/contracts` で共有スキーマを管理し、ペイロードに SemVer の `contract_version` を記録する。既存フィールドの意味を保ったまま任意フィールドを追加する変更は MINOR とする。同一 MAJOR の読み手は未知の任意フィールドを無視し、新しい読み手は追加フィールドを持たない旧版のペイロードも読み取る。必須フィールドの追加や既存フィールドの削除・型変更など、互換性を壊す変更は MAJOR とする。

新 MAJOR の提供開始日と旧 MAJOR の廃止日を事前に告知し、その期間は新旧の契約を併存させる。旧版のモバイルアプリは移行期間中も同期できる。発行済みの LINE 共有 URL は、API の旧 MAJOR 廃止後もアクセス権と有効期限の範囲で、保存時の契約に対応する読み取り経路から同じスナップショットを表示できるようにする。

### 3. 解析パイプライン・モデル

すべての解析結果に SemVer の `pipeline_version`、各ステージの `model_hash` と `license_tier`、`filter_spec_version`、`calibration_id`、`coordinate_revision_id` を記録する。`model_hash` は使用したモデル成果物の SHA-256 とし、モデルを使わないステージは `none` を明記する。校正を行わない場合も `calibration_id` に該当なしを明記する。ステージと設定、実際のフィルタパラメータ、校正誤差（該当時）も保存し、同一条件での再計算に使う。[ADR-0002](./0002-3d-motion-engine-selection.md)

エンジン更新後に再解析した結果は、元の試技に紐付く新しい不変の解析リビジョンとして保存する。元の結果もリビジョン ID で参照できるため、再解析結果との比較で両方の計測条件を確認できる。

### 4. 文献エビデンスレジストリ

レジストリはスキーマが定める SemVer の `evidence_registry_version` で管理する。各比較結果と LINE 共有 Web レポートに、生成時に使った正確な `evidence_registry_version` と評価済みの規範値スナップショットを固定する。スナップショットには参照した統計値、指標・イベント、単位、対象集団と標本数、計測方式、出典（著者・出版年・掲載誌・DOI・原典中の位置）、比較結果、非診断の注意文を含める。[Evidence Registry スキーマ](../evidence/evidence-record.schema.json)

ユーザーが最新版との比較を選んだ場合は、新しい比較結果を生成する。すでに共有した URL は発行時の解析リビジョンとスナップショットを参照し続ける。

## 検討した代替案

- **モノレポとアプリの単一バージョン**は見送る。モデル・校正・文献のどの条件で結果を生成したか識別できず、アプリや文献 DB だけの更新でも不要な再解析や共有レポートの互換性破壊を招く。
- **共有レポートから常に最新版の文献を参照**する案は却下する。文献の差し替え後に指導時と異なる値が表示され、当時の議論を同じ根拠で振り返れなくなる。

## 影響

モバイル、共有 Web、解析エンジン、文献 DB を独立した周期でリリースできる。解析リビジョンと比較スナップショットから、計測条件と参照した文献を監査できる。旧版ペイロードの読み取り互換性、移行期間中の API 併存、不変の解析リビジョンと比較スナップショットの保存を運用で維持する。

## 検証と強制

Phase 2 で共有契約と CI に以下を組み込む。[開発プロセス Phase 2](../03-development-process.md#phase-2-基盤ハーネス構築--垂直スライスfoundation-harness--walking-skeleton)

- **スキーマ検証**で `contract_version`、`pipeline_version`、`evidence_registry_version` の必須性と SemVer 形式を検証する。解析出力ではステージごとの `model_hash` を必須とし、SHA-256 を表す 64 桁の 16 進文字列、またはモデル不使用時の `none` のみを許可する。Evidence Registry の配布マニフェストのスキーマでは `evidence_registry_version` と配布ファイルの SHA-256 を必須とし、CI でレジストリ本体の版と実ファイルのハッシュに照合する。
- **契約互換性テスト**で、MINOR 更新のたびに旧ペイロードのフィクスチャを新しい読み手でデシリアライズできることと、新しい任意フィールドを含むペイロードを旧版の読み手でデシリアライズできることを確認する。
- **共有レポートの不変性テスト**で、発行済みの LINE 共有 URL を Evidence Registry の更新前後で取得し、固定された版、評価済みの規範値スナップショット、比較結果が完全に一致することを確認する。
